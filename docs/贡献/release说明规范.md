# Release 说明写作规范

Release notes 是**给使用者看的产品文档**，不是开发日志。陌生人打开应该能立刻
知道：这个版本能让我做什么新的事、有没有影响我现有代码的变化。

## 固定结构

按需选用，顺序固定，没有内容的小节直接省略：

```markdown
<一到两句话：这个版本带来什么能力。陈述句，不提"我""你"。>

## 新增
<每条一句话说清能力。语法特性必须配最小可运行代码示例。>

## 变更
<影响现有代码的改动。破坏性变更必须标注「破坏性」并给迁移写法。>

## 修复
<修了什么问题。描述**现象**（用户会遇到什么），不描述内部实现。>

## 已知限制
<还不支持什么。诚实列出，避免使用者踩空。>

---
测试：<数量> 个全绿。
```

## 语气规则

- **第三人称陈述**。不写「你」「我」「我们」，不写「按你的意见」「我顺手」。
  - ✗ `按你的意见改名。`
  - ✓ `输入函数更名，使其语义更明确。`
- **描述结果，不描述过程**。使用者关心「现在能怎么写」，不关心开发时怎么发现的。
  - ✗ `写示例时当场抓到这个 bug，139 个测试立刻红了。`
  - ✓ `修复：字典元素无法使用复合赋值（`字典[键] += 1` 解析报错）。`
- **不外泄内部约定**。`AGENTS.md`、决策编号（D-0xx）、内部代号一律不出现。
  项目内部规范属于贡献者文档，不属于发布说明。
- **不夸张**。避免「大山」「巡礼」「一针见血」这类修辞和评价性表达。
- **测试数量可以写**，它是质量信号；但不要叙述测试变红变绿的过程。

## 代码示例规则

- 每个语法新特性**必须**配一段最小可运行代码，让人直接看懂怎么写。
- 示例用 CNplus 代码，不用 Python 对照（除非该特性就是关于互操作的）。
- 示例必须真的能跑 —— 从 `示例/` 或测试里摘，不要手写臆造。

## 破坏性变更

必须显式标注，并给出「原来怎么写 → 现在怎么写」：

```markdown
## 变更

**破坏性**：输入函数更名。

| 原写法 | 新写法 |
|---|---|
| `问("提示")` | `询问("提示")` |
| `问数字("提示")` | `询问数值("提示")` |

旧名已移除。项目处于 0.x 阶段，不保留兼容别名。
```

## 标题

`vX.Y.Z — <四到八字的能力概括>`

- ✓ `v0.7.0 — 异常处理`
- ✓ `v0.4.0 — 列表、字典与循环`
- ✗ `v0.7.1 — 写真实程序抓到的两个 bug`（叙述过程）
- ✗ `v0.2.0 — 让零基础的人也能上手`（口号式）
